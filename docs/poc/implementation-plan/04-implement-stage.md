# Stage 4: Implement Stage

## Objective

Implement the only mutation-capable phase. It must execute an approved plan, keep changes within scope, run proportional verification, and record deviations and outcomes for independent review.

## Dependencies

- Stage 0 state and permission contracts.
- Stage 1 foundation.
- Stage 3 approval and plan-digest support.

## Deliverables

- `.agents/skills/implement/SKILL.md`
- `.agents/skills/implement/references/implementation-policy.md`
- `.agents/skills/implement/assets/implementation-template.md`
- `src/specromancy/phases/implement.py`
- `src/specromancy/artifacts/implementation.py`
- `src/specromancy/git.py`
- `src/specromancy/commands.py`
- `specromancy/templates/implementation.md`
- `tests/contract/test_implementation_artifact.py`
- `tests/evals/implement/`

## Input and output contract

Inputs:

- Approved `plan.md` with matching approval digest.
- Validated research and request artifacts.
- Repository state matching the recorded implementation baseline.
- Optional `review.md` when entering a repair cycle.

Outputs:

- Repository changes.
- `.specromancy/runs/<run-id>/implementation.md`.
- Captured verification command results.
- Updated Git head and changed-file inventory in `run.json`.

Required implementation artifact sections:

1. `## Summary`
2. `## Plan items completed`
3. `## Files changed`
4. `## Deviations from plan`
5. `## Verification performed`
6. `## Known limitations`
7. `## Review handoff`

## Skill behavior

The implementation skill must:

1. Verify status, plan approval, artifact digests, and repository baseline.
2. Acquire the run lock and transition to `implementation_in_progress`.
3. Read applicable nested instructions before editing their files.
4. Implement in the approved sequence unless a documented dependency requires reordering.
5. Preserve unrelated user changes and avoid broad destructive Git operations.
6. Add or update tests alongside behavior changes.
7. Run focused checks early and the approved broader verification before completion.
8. Stop for user approval when encountering a material scope change, dependency addition, destructive migration, secret requirement, or production action.
9. Record every plan deviation and whether it is material.
10. Produce `implementation.md`, validate it, and complete as `implementation_ready`.

For repair cycles, the skill must address review findings by ID and must not broaden the approved plan unless the user re-approves a revised plan.

## Repository baseline and scope controls

At phase start, record:

- current branch or detached-head state;
- `git rev-parse HEAD`;
- staged, unstaged, and untracked paths;
- plan-declared existing and new paths;
- paths already modified by the user.

The POC does not require a clean worktree. It must distinguish pre-existing changes from phase changes and preserve them. If a required file already has unrelated user modifications, the skill may continue carefully but must record the overlap.

Scope validation classifies changed paths as:

- planned;
- generated by a planned command;
- test or documentation support implied by a planned change;
- pre-existing user change;
- unexplained.

Unexplained paths fail completion until documented as an approved deviation or reverted by the actor that introduced them.

## Command execution records

For each verification command, record:

- exact argument vector or safely rendered command;
- working directory;
- start and end time;
- exit code;
- truncated stdout/stderr paths, stored separately when large;
- whether failure is blocking and why.

Never persist environment variables or secret values. The CLI provides command-record helpers; it does not attempt to sandbox arbitrary harness shell tools.

## Validator behavior

The implementation validator checks:

- valid approval still matches the current plan;
- changed-file inventory is current;
- every plan item is completed, deferred with a reason, or blocked;
- material deviations have user approval or force a return to planning;
- required verification commands ran and their recorded exit codes are acceptable;
- unexplained changed files are absent;
- implementation artifact contains no secret-like values;
- repair cycles reference every addressed review finding by ID;
- review cycle has not exceeded its bound.

## Implementation tasks

1. Build read-only Git helpers using subprocess argument arrays, never shell interpolation.
2. Capture baseline status and changed-file inventories.
3. Implement command execution records with output-size limits and redaction.
4. Create implementation template, policy reference, and canonical skill.
5. Implement start, completion, repair-entry, and abort handlers.
6. Implement plan-item and review-finding coverage validation.
7. Add stale-approval and concurrent-change detection immediately before completion.
8. Add run-lock acquisition, ownership diagnostics, and safe release.
9. Record implementation events and changed artifact digests atomically.
10. Add failure guidance distinguishing fixable test failure, approval-required deviation, and external blocker.

## Tests and evaluations

Contract tests:

- start without approval;
- stale approval digest;
- dirty worktree with unrelated pre-existing edits;
- planned and unplanned changed files;
- failed verification command;
- material deviation without approval;
- repair cycle with missing finding ID;
- lock contention;
- interrupted implementation and resume;
- output redaction and truncation.

Behavioral evaluations:

- localized bug fix with a regression test;
- feature spanning source, tests, and docs;
- existing user edit in an affected file;
- unexpected need for a new dependency;
- review repair with one valid and one invalid finding.

Score plan adherence, correctness, preservation of unrelated changes, verification quality, deviation reporting, and repair discipline.

## Exit criteria

- Implementation cannot begin from an unapproved or stale plan.
- Pre-existing user work remains identifiable and preserved.
- Changed files and verification results are reproducible from artifacts.
- Material plan drift reliably returns control to the user or planning phase.
- A reviewer can evaluate the change using repository state plus recorded artifacts only.

## Risks and mitigations

- **Agents bypass CLI helpers:** make the skill require CLI start/complete calls and detect repository changes at completion regardless of how they were made.
- **Unreliable command rendering:** retain argument arrays in JSON and use rendered strings only for display.
- **Dirty-worktree attribution errors:** snapshot path and status data, not just a single combined diff.
- **Overly rigid scope checks:** permit documented support files while requiring explicit classification.
