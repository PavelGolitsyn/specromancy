Resource-read order in `_new_visit` is: validate initial status, lookup phase,
calculate ordinal/attempt, resolve inputs in declaration order, render output,
reject reserved/existing output, hash skill, hash optional template, obtain active
start timestamp, construct record. Pending creation has no start timestamp.
A transition reads its output before checking limits, then seals the proposal
before successor observation. Activation and exact transition retries do not
refresh resources. Missing successor resources currently propagate their IO
error without committing the sealed proposal; changing that diagnostic is not
part of Stage 11.

## Approval order and durable boundary

- Request: strict load (including artifact and provenance checks), active/awaiting
  visit guard, declared reason, outcome, artifact validation, commands, mutation
  policy, required-command failure, then pending/approved selection. Even an
  identical pending request validates before returning. A successful fresh request
  stores evidence and its pending record in one `approval-requested` revision.
- Approve: persisted load first, visit/phase/idempotent checks, pending selection,
  output hash and pipeline binding check, durable invalidation on mismatch, then
  prepared-resource provenance check, decision timestamp, `approval-granted` commit.
- Continue approved: recheck artifact/pipeline binding, invalidate if stale,
  revalidate, then transition with saved outcome. Successful evidence is recorded
  in the transition commit; failed evidence gets one `validation-failed` commit.
  An unexpected command interruption propagates without that failed-attempt event.
- A grant never seals an output or creates a successor. From a pending request,
  successful approval adds two revisions/events (grant, transition); failed
  revalidation adds grant then failure; retry adds only a failure or transition.
  The original `approved` compatibility state already captures the grant/advance
  interruption, so no duplicate boundary test/capture was added.

Stage 13's [decided table](13-concurrent-approval-decisions.md#stage-09-decision-contract)
is future corrected behavior. The current before-grant overlap still asserts;
its winning command adds exactly grant and transition and the loser adds nothing.
The current after-grant overlap already transitions once. Stage 14's
