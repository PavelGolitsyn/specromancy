# 0.2.0 — Python namespace migration

Prepared on 2026-10-11 for local verification; no registry release is published
by this migration.

The `specromancy-engine` distribution now supplies the `specromancy_engine`
Python package. This is an intentional pre-1.0 API break with no legacy shim.

To upgrade:

1. Install the updated distribution in a dedicated environment. For development,
   run `python -m pip install -e .` again to refresh discovery and entry points.
2. Change `from specromancy import Engine` to
   `from specromancy_engine import Engine`, and change other imports and dotted
   mock targets to the new namespace. Facade names, exported objects,
   constructor signatures, exception identities, and compatibility aliases
   within the new namespace are preserved.
3. Replace `python -m specromancy` with `python -m specromancy_engine`.
   The installed command remains `specromancy`; checkout wrappers remain at
   `bin/specromancy` and `adapters/generate.py`.
4. Update source-relative schema references from `src/specromancy/schemas/` to
   `src/specromancy_engine/schemas/`. All four schema contents are unchanged.
5. Keep the installed console script on `PATH` when executing action packets.
   Their `final_validation_command` now starts with `["specromancy"]` rather
   than `[sys.executable, "-m", "specromancy"]`. The remaining arguments retain
   their values and order. Installation-free source-export users can put the
   checkout's `bin/` on `PATH`. Configured validation commands are untouched.

Import compatibility and persisted-state compatibility are independent. No
conversion of `.specromancy/runs/` is required: version-1 records, canonical
bytes, hashes, diagnostics, immutable outputs, approval checks, and recovery
behavior remain unchanged. Response shapes and schema versions are unchanged;
only the action command prefix intentionally differs. Historical fixtures are
preserved, with a separate `responses-0.2.0.json` expectation whose exact delta
is checked in compatibility tests.

Pipeline IDs, registry paths, generated skill names, harness directories, and
generator identity remain unchanged. Adapter rendering for identical test-owned
inputs still matches the original capture. Portable adapter invocation changes
are reserved for a later migration stage.
